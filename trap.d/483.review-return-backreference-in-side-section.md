An `oss:auditor` review spawn's final message (against commit 8159f47, issue #483) opened with
`FINDINGS: 2` and stated both findings completely, in full, as required. Its "could not check"
section -- a completely separate part of the message, unrelated to the findings themselves --
contained the sentence "I reproduced the scan only for the two directories this pass touches (see
above, and it matched)". Piped through `scripts/review_return.py --framed -`, this classified as
`referred-not-stated` (exit 3), not `states-findings`, because the `_BACKREF` regex in that script
matches `\b(?:see|per)[ \t]+(?:above|earlier|...)\b` anywhere in the message, with no scoping to the
findings section.

Confirmed by reading the script source directly: this is intentional and documented ("A back-reference
anywhere forecloses `states-findings`, however many markers trail it. That is not a heuristic bolted
on -- it is the rule the brief already states to the reviewer"). So this is not a bug in the
classifier, it is the classifier doing exactly what its own docstring says. What cost real time: the
first brief (agents/developer/review.md's own worked example) tells the reviewer "No `reported
above`, no `as noted`, no `detailed earlier`" but frames it as being about *findings specifically* --
a careful reviewer can and did read that as "don't gesture at unstated findings" and then wrote an
entirely honest, complete, self-contained sentence in an unrelated checklist section that happened to
use the word "above" to refer to its own immediately-preceding paragraph (not to a finding). The
result: a genuinely complete review (both findings independently verified as real by a later
re-spawn) was discarded as `returned-nothing`, costing one full ~11-minute re-spawn to recover
equivalent information.

What helped: writing the second brief (for the re-spawn, and again for two other spawns in the same
run) with an explicit instruction naming the exact phrases to avoid ("see above", "as noted",
"reported earlier", "per above", "mentioned above") and stating plainly that this applies to *every*
section of the message, not just the findings list, worked -- all three subsequent spawns in this run
that received that expanded instruction returned `states-findings` cleanly on the first try.

Unsure whether this is worth promoting into `agents/developer/review.md`/`review-return.md`'s own
brief template verbatim, or whether it is a one-off; logged for the curator to weigh. If it recurs,
the two-instance bar for a jit-context rule would already be met by this file plus a second sighting.
