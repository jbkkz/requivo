Two small tooling round-trips during the #483 pass5a lane, neither a defect, both worth a record.

**1. Writing a .pr.json PR-body payload via `paste`.** The body field needs literal JSON `\n`
sequences (one backslash, one `n`) to represent a paragraph break inside a JSON string. My first
attempt wrote `\\n` (a doubled backslash) inside the TOML literal, reflexively treating it the way you
would escape a newline in an ordinary shell string -- `paste` correctly refused it, naming every
occurrence and the two opposite fixes (halve it, or declare `literal_backslashes`). The fix that
actually worked: build the target JSON with Python's `json.dumps()` first (so it produces exactly the
single-backslash escapes JSON wants), write that string to a scratch file, then feed it into the TOML
literal with `literal_backslashes = ["content"]` so the already-correct single backslashes pass
through unmolested. Cost: one round trip per payload (this happened again, independently, while
writing this very trap file two minutes later -- a markdown code span containing a literal regex with
`\b`/`\t` also reads as "an even backslash run" to the same guard, and the fix there was simply to
halve it, not to declare `literal_backslashes`). The op's refusal message already names both fixes
correctly; the friction is entirely in remembering, per-field, which of the two the destination
format wants -- a JSON string field almost always wants "write JSON's own escaping, thus single
backslashes, thus half of what a reflex would type"; a documentation code span *showing* a regex
pattern also wants single backslashes (the pattern itself), so the fix in practice was the same
("halve it") in both cases despite one target being `.json` and the other `.md`. The op's own
guidance already says this ("the target here is .md -- prose rarely wants a literal doubled
backslash: the FIRST fix... is the common case") -- reading that line the first time rather than after
a refusal would have saved the second round trip.

**2. `supertool git-commit` with modified-but-unstaged files.** Calling `git-commit:@-` with only a
`message` field and no `paths`, when the working tree has modified tracked files, refuses outright
("no PATHS were given -- git-commit never stages for you") rather than staging everything implicitly.
This is correct behaviour and the refusal message names the fix precisely (either a `:::`-joined path
list, or a `paths = [...]` array in the same heredoc). Cost: one round trip, entirely avoidable by
reading the op's own contract before the first call rather than after the first refusal -- unlike
item 1 above, this one has an unambiguous single fix and no ambiguity to resolve, so it is closer to
"read the manual" than to a genuine tooling gap.
