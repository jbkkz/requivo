Observed three times in one lane (#519), on `paste:@-` and `edit:@-` payloads carrying Python
source in a TOML triple-single-quote literal block: I wrote a Python string literal for a newline
as a backslash followed by a backslash and an `n` (the "escape it for the transport" reflex), and
supertool refused each payload with the #2314 even-backslash-run check. The refusal is correct and
the message is clear; the cost was three round-trips, because the reflex fired again after reading
the message, on the next file. In the third case the file also legitimately needed a doubled
backslash (`_cell` escapes a pipe as backslash-pipe, and the test asserts on that), so the
resolution was mixed: halve the newline runs, and name `literal_backslashes = ["content"]` for the
one field where the doubled run is meant as written.

A fourth round-trip came from writing this very fragment: quoting the triple-single-quote delimiter
inside the block it delimits closed the block early ("bad key at offset 187"). Spell it out in
words instead.

What confirmed it: after halving, the written file parsed and the tests ran; the one exempted run
reached disk as two characters, which the assertion needed.

Not sure it is a rule beyond "a literal block processes no escapes -- write the bytes you want on
disk", which the developer brief already states in as many words. The observation worth keeping may
be that the brief's sentence does not survive contact with a Python newline literal in the payload:
the reflex is specific to writing *source code* in a transport that also has an escape syntax, and
a `.py` target is the case the refusal message itself calls the common one. Logged for the curator
to decide whether that deserves a line of its own next to the existing rule.
