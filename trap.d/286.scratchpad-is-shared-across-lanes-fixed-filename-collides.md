# The session scratchpad is shared across concurrent lanes; a fixed filename there is overwritten by a sibling

Observed on 2026-09-12 in lane #286, with seven sibling lanes running (524, 530, 519, 483c, 425b,
493, 258).

The environment preamble names a scratchpad directory
(`/private/tmp/claude-501/<project>/<session-id>/scratchpad`) and calls it "session-specific,
isolated from the user's project". In a fleet every lane spawned from the same coordinator session
receives the *same* directory: `ls` of it showed `before_530.json`, `before-425b-slice4.json`,
`commit_msg_530.txt`, `fix-519-msg.txt`, `pr524.json`, `ts-483c.txt` beside my own files.

What it cost: I wrote `tree_snapshot.py snapshot` output to `scratchpad/before.json` (a fixed
name) before spawning my reviewers. The printed root/branch at that moment was my own
(`requivo-wt/286`, `fix/286`). When both reviewers returned I piped that file into
`tree_snapshot.py compare --before -` and got
`VERDICT: mutated -- HEAD moved from ceff80e... to 912264c...` — neither hash was mine. The file
now read `"root": ".../requivo-wt/493", "branch": "fix/493"`: lane 493 had written its own
snapshot to the same fixed name in between (mtime 08:24, mine was 08:1x). One round-trip to
diagnose, and the receipt the phase file asks for had to be reconstructed by hand (the snapshot
schema is small enough to rebuild from the printed line plus `git rev-parse`, and the tree hash
`HEAD^{tree}` gave the byte-identical proof the compare could not).

Confirmed by: the file's `root` field, the `ls -la` mtimes, and the sibling-named files in the
same directory. `agents/developer/report.md` already warns that the scratchpad is shared and asks
for branch/timestamp discriminators on *report-phase* intermediates; the `review.md` snippet that
writes `$BEFORE` keeps it in a shell variable, which is safe — I lost it by persisting it to a
fixed-name file so it would survive across Bash calls. Any file that has to outlive one Bash call
needs the same `<branch>-<timestamp>` discriminator, or its content is not yours when you read it
back.

Not sure whether this is one rule or a correction to the environment preamble's "session-specific"
claim; logging it either way.
